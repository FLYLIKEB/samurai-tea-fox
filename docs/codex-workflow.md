# Codex 실행 절차

이 문서는 Codex가 `무차우: 한 잔의 도` 구현 작업을 수행할 때 따르는 반복 절차다. 최상위 규칙은 루트 [AGENTS.md](../AGENTS.md)를 따른다.

## 기본 원칙

- 한 번에 GitHub Issue 또는 Notion `🤖 AI 구현 백로그` 항목 하나만 처리한다.
- 작업 범위는 현재 Issue가 정한다.
- 작업마다 별도 Git branch와 별도 worktree를 만들고, 구현·테스트·커밋·PR은 그 worktree에서만 수행한다.
- 작업 완료 후에는 로컬 기준 checkout을 `main`으로 복귀시키고 `origin/main`과 fast-forward 동기화된 상태에서 완료 보고한다.
- 기획, 콘텐츠, 밸런스 판단은 Notion 정본을 확인한 뒤 수행한다.
- 저장소 현재 구현을 먼저 읽고, 이미 있는 구조를 확장한다.
- 범위 밖 발견 사항은 구현하지 않고 후속 Issue 후보로 남긴다.

## 시작 전 확인

1. `git status --short`로 worktree 상태를 확인한다.
2. 현재 브랜치와 remote를 확인한다.
3. 관련 없는 local change가 있으면 덮어쓰거나 PR에 섞지 않는다.
4. 루트 `AGENTS.md`를 읽는다.
5. `docs/architecture.md`, `docs/export-targets.md`, `docs/notion-source-map.md`에서 관련 구현 경계를 확인한다.

## Notion 확인 순서

1. `무차우: 한 잔의 도 — 게임 컨셉 바이블`을 라우팅 인덱스로 확인한다.
2. `00. 기획 아키텍처·정본 규칙`을 확인한다.
3. `12. 기술 스펙·아키텍처`를 확인한다.
4. 현재 작업의 `🤖 AI 구현 백로그` 항목을 확인한다.
5. 백로그 항목에 연결된 관련 기획 문서만 확인한다.
6. 정확한 콘텐츠 값이나 수치가 필요하면 관련 정본 DB 행을 확인한다.

`전체 정본 확인`은 모든 Notion 페이지를 전부 읽는다는 뜻이 아니다. 루트 인덱스로 책임 위치를 확인하고 현재 Issue에 필요한 정본만 조회한다.

## DEV 항목 지정 실행

사용자가 `DEV-7`처럼 특정 DEV 항목을 지정하면 다음을 따른다.

1. Notion 백로그에서 해당 DEV 항목을 정확히 찾는다.
2. `상태`가 `진행 중` 또는 `완료`이면 새로 구현하지 않는다.
3. 목표, 범위, 비범위, 완료 조건, 검증 방법, 선행조건을 읽는다.
4. 선행조건이 미완료이면 구현하지 않고 차단 사유를 보고한다.
5. 선행조건이 완료되어 있으면 GitHub Issue 중복 여부를 확인한다.
6. 기존 Issue가 있으면 재사용하고, 없으면 새 Issue를 만든다.
7. 전용 branch와 worktree를 만든다.
8. Notion과 GitHub Issue에 작업 시작 표시를 남긴 뒤 해당 Issue 범위만 구현한다.

비슷한 DEV 항목으로 대체하지 않는다.

## 작업 선점과 중복 방지

Notion `🤖 AI 구현 백로그`의 상태 필드는 `상태`이고 옵션은 `시작 전 / 진행 중 / 완료`다.

- 자동 선택 후보는 `상태 = 시작 전`으로 제한한다.
- `상태 = 진행 중`인 백로그는 다른 에이전트가 작업 중인 것으로 보고 선택하지 않는다.
- 사용자가 명시한 DEV 항목이라도 `진행 중`이면 takeover 지시 없이는 구현하지 않는다.
- GitHub Issue에 작업중 라벨, 열린 연결 PR, 최근 `Codex 작업 시작` 코멘트가 있으면 작업중으로 본다.
- 같은 DEV ID를 포함한 로컬 branch나 worktree가 있으면 먼저 해당 작업 상태를 확인한다.

구현 파일을 수정하기 전에 다음 표시를 완료한다.

1. Notion 백로그 `상태`를 `진행 중`으로 변경한다.
2. Notion 백로그 `GitHub Issue`에 사용할 Issue URL을 기록한다.
3. GitHub Issue에 `status: in-progress` 또는 `codex-working` 라벨을 붙인다.
4. GitHub Issue에 `Codex 작업 시작` 코멘트를 남기고 branch, worktree, 시작 시각을 적는다.

Notion 또는 GitHub Issue에 작업 시작 표시를 남길 수 없으면 구현을 시작하지 않는다.

## 다음 실행 가능 항목 자동 선택

DEV 항목이 지정되지 않았으면 Notion 백로그에서 정확히 한 건만 고른다.

선택 기준:

1. 선행조건이 완료됨.
2. `상태`가 `시작 전`임.
3. AI 단독 구현이 가능함.
4. 우선순위가 가장 높거나 구현 순서가 가장 빠름.
5. 완료 조건과 검증 방법이 명확함.
6. 동률이면 의존성 표면이 가장 작음.

선택 근거를 짧게 남긴 뒤 Issue 발행과 구현으로 진행한다.

## 구현 절차

1. 전용 branch/worktree 안에서 현재 구현 구조와 관련 모듈을 읽는다.
2. 관련 테스트와 데이터 파일을 확인한다.
3. Issue를 만족하는 가장 작은 응집된 변경 범위를 정한다.
4. 기존 모듈 경계를 지키며 구현한다.
5. 필요한 경우에만 정적 export 데이터나 schema를 수정한다.
6. 변경한 규칙에 맞는 테스트를 추가하거나 수정한다.
7. targeted test를 먼저 실행하고, 필요하면 Godot import/build/smoke check를 실행한다.

## 중지 조건

다음 상황에서는 추측으로 진행하지 않는다.

- Notion 백로그 항목을 찾을 수 없음.
- 선택한 백로그 항목이 이미 `진행 중` 또는 `완료` 상태임.
- 선행조건이 미완료이거나 모호함.
- Issue를 만들 만큼 목표·범위·검증 기준이 부족함.
- GitHub 인증 또는 권한이 없음.
- Notion 또는 GitHub Issue에 작업 시작 표시를 남길 수 없음.
- 관련 없는 local change가 PR에 섞일 위험이 있음.
- 검증 실패를 현재 Issue 범위 안에서 해결할 수 없음.

멈출 때는 확인한 증거, 차단 사유, 필요한 최소 다음 조치를 보고한다.

## 완료 기준

- GitHub Issue가 생성되었거나 기존 Issue가 재사용되었다.
- 구현 시작 전에 Notion과 GitHub Issue에 작업 시작 표시를 남겼다.
- 구현이 Issue 범위 안에 머물렀다.
- 관련 Notion 문서와 정본 DB를 확인했다.
- 관련 테스트 또는 동등한 검증이 성공했다.
- PR이 생성되었거나, PR 생성 실패 사유가 명확히 보고되었다.
- 완료 보고 직전 로컬 기준 checkout이 `main`이고 `origin/main`과 동기화되었다.
